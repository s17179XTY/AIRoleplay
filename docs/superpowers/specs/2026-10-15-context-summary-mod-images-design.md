# 上下文窗口、摘要记忆库、MOD、图片与同步冲突 —— 设计文档

> 日期：2026-10-15
> 前置：本文件取代 `docs/superpowers/specs/2026-10-14-account-sync-design.md` 中「记忆托管」的相关描述；
> 账号/同步/加密部分不变。

---

## 0. 背景与目标

### 0.1 现在的问题

1. **上下文没有任何控制。** `streamReply()` 把整条世界线（从根到当前叶子）全部塞给 `assemble()`；
   唯一的限制是 token 预算 `contextLength − maxTokens − 512`，而 `contextLength` 默认 1,000,000，
   且**在界面上根本改不了**（`supportedFields` 里没有它）。实际行为＝「全塞，塞不下才砍最老的，砍掉就真丢了」。
2. **记忆库的定位是错的。** 现在它把 AI 回复里 `<details>近期记忆/永久记忆</details>` 解析出来存两层
   （近期 + 溢出归档成永久），但 AI 的回复本身就在历史里 —— 存一份几乎不增加信息量。
   而且 `ingestMemories()` **无去重、直接 add**，模型每轮重写整份清单时会存出重复条目。
3. **被挤出窗口的对话没有被记录下来。** 版面上砍掉的旧消息彻底消失。
4. **窗口内的消息还会被剥离记忆块**（`stripMemoryAndThink`），一旦解析失败，那段摘要再也不会进提示词。

### 0.2 目标

- 给用户**上下文控制**：送多少条消息、模型的上下文有多大，两个都自己定。
- 把记忆库改成**摘要库**：只装「掉出上下文窗口的交换」的压缩结果，由模型压缩、按对压缩、保留发送者。
- 掉出窗口的东西**必须有摘要接管**，不允许凭空消失。
- 聊天页能看到**上下文占用与轮数**。
- 顺带把用户报的其他问题与三个新子系统（同步冲突取舍、MOD、图片）一起做完。

### 0.3 已定案的规则（用户逐条确认过）

| # | 规则 |
|---|---|
| 1 | 摘要库只放「掉出上下文窗口的那些交换」的压缩结果；窗口内的消息保持原文，一字不动 |
| 2 | 由**模型**压缩（不使用「免费摘 AI 记忆块」那套，已作废） |
| 3 | 触发阈值：**只要有 1 条消息超出窗口就算攒够**，立刻压；开关**默认开** |
| 4 | 压缩单位：**一对一对，绝不压半对**。窗口切点落在一对中间时，把整对都算掉出窗口 |
| 5 | 必须保留发送者：摘要分「用户」与「AI」两部分存储，注入时也分开、带标签 |
| 6 | 压缩期间**禁止发送**；显示「正在整理之前的记忆…」，可取消（取消则不写入，下次再试） |
| 7 | 压缩失败**不吞掉**：该段保持未摘要，下次发送前重试 |
| 8 | 旧记忆条目**强制清掉**，逐条 `delete(id)`（产生墓碑 → 连云端一起清）；**禁止用 `clear()`** |
| 9 | 摘要限长、**计入 token 预算、可被裁**、库内上限 20 条，超出时把最老 5 条本地拼接成一条 |
| 10 | 「最近 N 条」与「全部带」两种模式共用同一套摘要机制，只是判定「掉出」的方式不同 |

补充确认的 7 条提议（全部采纳，第 3 条改为「文学描写」）：

1. 同一轮掉出的多对**合并成一次压缩请求**，输出按「用户方 / AI 方」两段归纳。
2. 摘要走 **system 条目 + 明确标签**注入，**不用** user/assistant 角色注入
   （Anthropic 等要求 user/assistant 严格交替，插角色消息会变成 `assistant, assistant` 直接报错）。
3. 摘要用**文学描写**写（不是干巴巴的事实清单），但必须硬性保留：人物与关系变化、关键事件、
   当前时间/地点/身体与情绪状态、已确立的约定或规则。
4. 压缩时把**上一条摘要**（尾部 200 字）一起给模型，让它接着写而不是孤立成段。
5. HUD 里显示摘要库占用。
6. 摘要条目可**手动编辑/删除**。
7. 「用户消息还没有 AI 回复」的半对**不压**，等它有了回复再一起压。

## 1. 上下文窗口

### 1.1 设置

| 放哪 | 键 | 默认 | 说明 |
|---|---|---|---|
| 模型配置（`modelPresets.params`） | `contextLength` | 1,000,000 | **新增到参数滑块**（数据结构里本来就有，只是没露出来） |
| 全局设置（`settings`） | `contextMode` | `'recent'` | `'recent'`＝只带最近 N 条；`'all'`＝全部带 |
| 全局设置（`settings`） | `contextMessageLimit` | `6` | 只在 `recent` 模式下生效 |
| 全局设置（`settings`） | `summaryEnabled` | `'1'` | 「记忆托管」开关的新语义：要不要自动生成摘要。关掉＝完全不生成、不注入摘要 |
| 全局设置（`settings`） | `summaryBatchPairs` | `'1'` | 攒够几对掉出才压。默认 1（符合「只要有 1 条超出就压」），可调到 2–5 省钱 |
| 全局设置（`settings`） | `memorySchema` | （无） | 迁移标记，见第 4 章 |

界面文案必须写清代价：**「最近 N 条」省钱 / 「全部带」记得多**。

**删除**「近期记忆保留条数」这个设置（连同它的「保存时才检查」提示）—— 在新设计里它已经没有意义。
`configs.memoryLimit` 字段保留在类型里（旧数据兼容），但不再被读取。

### 1.2 窗口怎么算

```
最近 N 条：window = 世界线最后 N 条消息；比这更早的算「窗口外」
全部带    ：window = assemble() 预算裁剪后真正保留的那些历史条目；被 dropped 的算「窗口外」
```

- **`N` 是「不含本轮输入」的历史条数**（本轮输入在 `assemble` 里是独立的 `userInput`）。
- **「条」＝ user 与 assistant 各算一条**（用户原话是「最后新的 6 个消息（包括用户和 AI 的）」）。

**只认 `assemble()` 的结果作为事实来源**，不另算一遍，避免两处逻辑漂移。

### 1.3 「成对」规则（落地写法）

- 配对：一条用户消息 + 它后面紧跟的那条 AI 回复＝一个交换。
- **向外扩边**：若窗口切点落在交换中间（AI 回复还在窗口内、它的用户输入已出去）→
  **整个交换都算窗口外**，一起压。这就是「绝不压半对」。
- **未完成的交换（暂缓，不是丢弃）**：用户消息还没有 AI 回复时（例如上一次生成被停止），
  它配不成对 → **本次不压**，标记为 pending；等 AI 回复落地后，立刻连同前面的一起补压。

## 2. 记忆库 → 摘要库

### 2.1 数据模型：改造 `memories` 表，不新增表

理由：`memories` 已存在、已会同步（`memory` 这个 sync kind 不动）、备份/清空/重置全部自动带上。

```ts
export interface MemoryRecord {
  id: string;
  chatId: string;
  tier: 'summary' | 'recent' | 'permanent';   // 新写入的只有 'summary'；后两个只用于迁移期识别旧数据
  text: string;                                // 完整摘要（含分段内容）
  userText?: string;                           // 「用户」那一段
  assistantText?: string;                      // 「叙事（AI）」那一段
  dateLabel: string;                           // 时间范围，例如「10-01 ~ 10-03」
  order: number;
  sourceMessageId: string | null;              // = 覆盖到的最后一条消息 id
  archivedAt: number | null;
  // 新增（均非索引字段，Dexie 不需要升版）
  fromMessageId?: string;
  toMessageId?: string;
  messageCount?: number;
  origin?: 'model' | 'merged' | 'local-skeleton';
  tokenCount?: number;
  createdAt?: number;
}
```

### 2.2 记录（写入）时机与内容

每次**发送前**组提示词时：

1. 按第 1 章算出窗口。
2. 找出「窗口外、且没有被任何摘要覆盖」的消息范围。
3. 按第 1.3 的成对规则扩边，得到要压缩的完整交换集合。
4. 若集合里的完整交换数 **≥ `summaryBatchPairs`（默认 1）** → 生成**一条**摘要：

| 情况 | 处理 |
|---|---|
| `summaryEnabled` 开（默认） | 发一次压缩请求（第 2.3 节）；失败则保留 pending，下次发送前重试（规则 7） |
| `summaryEnabled` 关 | **完全不生成摘要**（也不注入）。用户自己承担长对话的失忆 |
| 某一批**连续失败 3 次** | 退化为**本地骨架摘要**（`origin: 'local-skeleton'`）：「第 X–Y 条 · 用户输入前 40 字 · 时间范围」，UI 标注来源。**宁可粗糙也不能丢** |
| 模型输出拆不出「用户/叙事」两段 | 整段存进 `text`，`origin` 仍是 `model`，UI 提示「格式未识别」 |

### 2.3 压缩请求

- **只带掉出窗口的那一批消息**（+ 上一条摘要的尾部 200 字），**不带整个上下文**。
- 提示词（写在 `src/core/sync` 之外的新模块 `src/core/memory/summarize.ts`）：

```
你在帮一个角色扮演应用整理长期记忆。把下面这一段对话压缩成一段摘要：

1. 用叙事性的文学笔法写，保留细节与氛围，不要写成干巴巴的条目列表。
2. 必须保留：出现的人物与其关系变化、已发生的关键事件、当前时间/地点/身体与情绪状态、
   任何已经确立的约定或规则。
3. 分两部分输出，各自以固定标记开头：
   用户：<玩家这一方说过、做过、选择过的事>
   叙事：<AI 这一方写过的事>
4. 每部分不超过 200 字。
5. 不要添加原文没有的内容，不要评论，不要输出其它内容。
```

- 解析：抓 `用户：` / `叙事：` 两个标记；抓不到就整段当 `text`（`userText`/`assistantText` 留空）。
- 计入「摘要生成」这个独立状态，**期间禁用发送**（见 2.5）。

### 2.4 上限与分层压缩

- 每段限长 200 字（输出后截断）。
- 摘要条目**计入 token 预算，可被裁剪**（与历史同组，先裁最老的摘要）。
- 库内最多 **20 条**；超出时把最老的 5 条**本地拼接**成一条（`origin: 'merged'`），
  拼接时保留「用户 / 叙事」分段与时间范围。库里长期维持在 ~20 条。

### 2.5 状态与并发

- 新增会话状态 `summarizing: boolean`（与 `streaming` 并列）。
- `summarizing === true` 时：输入框仍可打字，但**发送禁用**，停止按钮显示为「取消整理」。
- 顺序：`send()` → 先做摘要（若需要）→ 再做主生成。这样天然被现有互斥挡住，不会两条流并发。
- 取消：不写入摘要，把该范围标记回 pending，下次发送前重试。

## 3. 注入位置与格式（用户补充要求：**放对位置，避免 AI 以为是最新资讯**）

### 3.1 最终注入顺序

```
卡片·前缀词(pre) → 全局·提示词(system 10) → 全局·前缀词(system 20) → 卡片·提示词(system 30)
→ MOD(system 35) → 主人公设定(41) → 前情提要(42) → 互动页【初始信息设定】(45)
→ 世界书(before-history 50+/100+)
→ 【更早的对话摘要】(before-history 200+)   ← 紧贴历史之前
→ 历史（窗口内原文；**不再剥离记忆块**）
→ 全局·后置词(after-history 30) → 卡片·后置词(post) → 本轮输入(post)
```

（卡片**简介**原本在 system 40，第 9 章第 1 条会把它从注入里拿掉，所以这里已经没有它。）

### 3.2 摘要区块的格式

摘要**整体**是一条 `system` 条目，`source: 'memory'`，`position: 'before-history'`，`priority: 200 + order`：

```
【更早的对话摘要 · 以下内容发生在当前对话之前，不是最新消息】
时间范围：10-01 ~ 10-03（共 12 条消息）

— 摘要 1（10-01 ~ 10-02，6 条）—
[用户] ……
[叙事] ……

— 摘要 2（10-02 ~ 10-03，6 条）—
[用户] ……
[叙事] ……

【以上是更早的摘要，以下是最近的原文对话】
```

三条硬性要求：

1. **标题就写「不是最新消息」**，位置也紧贴历史之前 —— 避免 AI 把摘要当成本轮输入。
2. 摘要按时间**从旧到新**排列，与历史的时间方向一致。
3. 历史与摘要之间有一行明确的分隔提示。

### 3.3 不再剥离记忆块

- 窗口内的消息**保留** AI 写的 `<details>记忆</details>` 原文（它本身就是上下文的一部分）。
- `<think>` / HTML 注释照旧剥离（那只是模型的思考噪音）。
- 于是 `stripMemoryAndThink()` 拆成两个函数：保留 `stripThink()`，删掉「剥记忆」那半个动作。
  **Q1（剥了但没入库 → 信息丢失）从此不存在。**

## 4. 旧数据迁移（用户要求：强制清掉）

启动时检查 `settings.memorySchema`：

- 若不是 `'summary-v1'`：
  1. 取出 `memories` 中 `tier !== 'summary'` 的所有行；
  2. **逐条** `db.memories.delete(id)`（**不能用 `clear()`** —— `clear()` 走 deleteRange，
     而 outbox 收敛点刻意不对 deleteRange 产生墓碑，云端那份会在别的装置被拉回来）；
  3. 写入 `settings.memorySchema = 'summary-v1'`。
- 完成前不生成任何新摘要，避免新旧混在一起。

## 6. 同步冲突取舍（用户已按建议拍板）

### 6.1 现状

- 规则是 LWW（后推的赢）；冲突时被覆盖的那一版进 `syncConflicts`（只存密文），UI 只显示数量。
- 登录＝云端赢；注册＝本地单向认领。

### 6.2 改法

**登录时的预检与选择**（`login()` 拿到 token 之后、`runSync()` 之前）：

1. 本地内容表是否非空？＋ `GET /api/me` 的 `quota.used > 0`（云端是否非空）？
2. 两边都非空 → 弹一次选择：

| 选项 | 行为 |
|---|---|
| **以云端为准**（默认） | 直接 pull；被覆盖的本地版本进冲突面板 |
| **以本地为准** | 顺序必须是 **① 先给本地内容表拍快照 → ② pull 一次（拿到 rev，同时接受云端数据）→ ③ 用快照覆盖回本地 → ④ 推上去**。被覆盖的云端版本进冲突面板 |

> ③ 不能省：pull 会先把云端内容写进本地表，不快照就等于「选中了本地为准、结果还是云端赢」。
> 也不需要服务端加「强制推送」——pull 之后本地 rev 与云端一致，正常 push 就会被接受。

（原本设想的「两者都留」不做 —— 那正是冲突面板在做的事，不需要第三条路径。）

3. 任一边为空 → 不弹，直接按现有流程（空云端＝首次上传；空本地＝首次下载）。

**冲突面板可看可还原**：`syncConflicts` 里存的是密文，但 DEK 在内存里，可以解密后展示：

- 列表：表名 / 记录 id / 被覆盖时间 / 内容摘要（例如消息 `raw` 前 80 字）。
- 操作：**「用这一版覆盖回去」**（解密 → 写回原表 → 排队推送 → 更新 `syncRev`）/「丢弃」。

## 7. MOD（热插拔提示词）

### 7.1 定位

一段可开关的提示词，**套用后立即生效** —— 因为每轮都重新 `assemble()`，改 `enabled` 天然就是下一轮生效，
不需要任何额外机制。

### 7.2 数据

新表（Dexie v3 只加表）：

```ts
export interface ModRecord {
  id: string;
  name: string;
  content: string;
  enabled: boolean;
  order: number;
  createdAt: number;
  updatedAt: number;
}
// stores: 'mods': 'id, enabled, order'
```

- **scope 只做全局**（用户明确要求，YAGNI）。
- 内容支持宏（`{{char}}` `{{user}}` 等），与其他条目一样走 `applyMacros`。
- 同步：`SYNC_TABLES` 新增 `mod: 'mods'`（14 → 15 种）。连带要改：
  `kinds.test.ts` 的数量断言、`backup.ts` 的导出/导入表清单。
- 注入：`assemble()` 新增 `mods` 输入，`position: 'system'`、`priority: 35`（接在卡片提示词之后）。

### 7.3 UI

- **设置页新增「MOD」分节**：列表（名称 / 开关 / 上移下移 / 编辑 / 删除）+「+ 新增 MOD」（名称 + 提示词内容）。
- **聊天页顶栏加入口**（chip「MOD n」）：点开小面板，可以**当场开关**，不用回设置页。

## 8. 图片：卡片封面 + 聊天头像

### 8.1 范围

只做**卡片外**的两张图（用户明确）：**卡片列表的封面** ＋ **聊天时的头像**。
不做卡片内置页里的图片管理。

### 8.2 数据

- `CardRecord.coverAssetId?` **已存在**（`saveCardPackage` 会写）；新增 `CardRecord.avatarAssetId?`（非索引字段，不用升版）。
- 图片本体照旧存 `assets` 表 + `cardFiles`（`kind: 'asset'`，路径 `assets/cover.*` / `assets/avatar.*`）。
- 同步走**已有的** `assetMeta` 加密 blob 通道 —— 不需要新的同步代码。

### 8.3 上传与校验

1. `<input type="file" accept="image/png,image/jpeg,image/webp,image/gif">`
2. 校验（**真正的防护在这里**，不是账号门槛）：
   - **magic byte 白名单**：PNG `89 50 4E 47` / JPEG `FF D8 FF` / GIF `47 49 46 38` / WebP `RIFF….WEBP`；
   - **明确不接受 SVG**（SVG 可以带脚本）；
   - 原文件 ≤ **2 MB**；解码后最长边 ≤ 4096（防解压炸弹）。
3. 压缩后再存：封面最长边 512 px、头像 128 px，输出 WebP（不支持则 JPEG），通常 < 100 KB。
4. 渲染一律走 `<img src=objectURL>`，**绝不 inline SVG/HTML**。

### 8.4 账号门槛（用户要求）

- **没登录**：「+ 上传图片」按钮**禁用**，提示「登录后才能上传图片」；**已有的图片照常显示**。
- **已登录**：可以上传，并自动走加密 blob 同步。
- 注意：这是**产品门槛，不是安全边界**（谁都能注册）。安全靠 8.3 的校验。
  这一句要写进代码注释，避免以后误以为它是防护。

### 8.5 导出策略

- **全量备份**（`exportAll()`）**包含**图片（换机要能带走）。
- **导出卡片包**（`packCard`）**默认不含图片**（用户要求，避免夹带），
  导出时弹一个小选择：「不含图片（默认）/ 包含图片」。
  实现上 `packCard` 增加一个 `{ includeAssets?: boolean }` 参数。

## 10. 受影响的既有行为与风险

1. **默认行为会变**：从「全塞进 100 万 token」变成「只带最近 6 条 + 摘要」。想维持原样就在设置里选「全部带」。
2. **世界书触发范围变小**：关键词匹配只看窗口内那几条 + 本轮输入。互动页的【初始信息设定】不受影响（system 层，永远带着）。
3. **摘要质量决定长期连贯性**：窗口只有 6 条时，摘要是长期剧情的主要载体。所以第 2.3 节的压缩提示词与
   「文学描写但保留硬事实」的要求非常关键。
4. **每次掉出窗口都会多一次很小的模型调用**（只带那一对，输入很小）。窗口满了之后大致每 2 轮一次。
   提供 `summaryBatchPairs`（默认 1）作为成本调节杠杆。
5. 内置卡提示词里那段「记忆结构定义与规则」**保留**（AI 还在写记忆块，属于上下文的一部分），
   但把「最大 6 条近期记忆」这类措辞改成中性描述 —— 需要再升一次卡片版本。
6. **图片门槛不是安全边界**（见 8.4）。
